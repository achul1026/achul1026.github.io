## 먼저 결론

- 파티셔닝, 인덱스, 집계 테이블은 질의마다 효과가 달랐습니다. 같은 기법이 어떤 질의에서는 28배 빨라졌고, 어떤 질의에서는 2배 넘게 느려졌습니다.
- 집계 테이블이 가장 크게 효과가 있었습니다(225~307배). 대신 데이터가 늦고, 집계 단위에 없는 질문은 받을 수 없습니다.
- API 계층에서는 캐시보다 **캐시가 죽었을 때의 동작**이 더 중요했습니다. Redis를 끄자 요청당 1초가 걸렸고, 서킷 브레이커로 20ms까지 되돌렸습니다.

모든 수치는 [traffic-stats-lab](https://github.com/achul1026/traffic-stats-lab)에서 직접 측정한 값입니다.

## 왜 다시 측정했나

이전 프로젝트에서 교통 데이터 통계 화면이 수십 초씩 걸리는 문제를 다룬 적이 있습니다. 쿼리 튜닝, 연·월 단위 파티셔닝, 집계 테이블, 인덱스를 차례로 적용해서 10초 안으로 줄였습니다. 다만 그때는 무엇이 얼마나 효과가 있었는지를 하나씩 떼어서 확인하지 못했습니다. 업무 데이터는 공개할 수 없으니, 비슷한 구조의 가짜 데이터로 처음부터 다시 측정해 보기로 했습니다.

먼저 밝혀 두면, 실제 업무의 규모와 이 실험(약 1.7GB)은 크게 다릅니다. 이 글의 수치를 그때의 성과와 직접 비교하시면 안 됩니다. 이 글에서 보고 싶었던 것은 기법별로 어떤 질의에서 효과가 있고, 어떤 질의에서는 오히려 손해인지입니다.

## 실험 조건

- 합성 교통 관측 데이터 3,000만 건 (31개 지역, 2023-01 ~ 2024-12, 균등 분포)
- PostgreSQL 18.3, 노트북 1대(i5, RAM 8GB). 조회 시간은 `EXPLAIN (ANALYZE)`의 실행 시간
- 워밍업 1회 후 5회 측정, 중앙값 사용
- 구성 5가지: (A) 단일 테이블 (B) 월 파티션 (C) 단일 + 인덱스 (D) 월 파티션 + 인덱스 (E) 일 단위 집계 테이블
- 질의 4가지
  - Q1: 지역 하나의 3개월 월별 통행량
  - Q2: 전 지역 한 달 일별 평균 속도
  - Q3: 도로 하나의 1년 시간대별 평균 속도
  - Q4: 지역별 연간 통행량 순위

측정 전에 모든 구성이 같은 답을 내는지부터 확인했습니다. 빨라졌는데 답이 틀리면 의미가 없으니까요.

## 결과

| 질의 | A 단일 | B 월 파티션 | C 단일+인덱스 | D 파티션+인덱스 | E 집계 테이블 |
|---|---|---|---|---|---|
| Q1 | 1,783ms | 290ms | 746ms | 500ms | 5.8ms |
| Q2 | 2,525ms | 2,414ms | **5,559ms** | 2,584ms | 11ms |
| Q3 | 1,757ms | 744ms | 62ms | 47ms | - |
| Q4 | 2,947ms | **6,774ms** | 4,825ms | 4,139ms | 12ms |

![질의별 조회 시간](/assets/images/01_db_조회시간.png)

굵은 숫자가 눈에 걸립니다. Q2에서 인덱스를 걸었더니 2.5초가 5.6초로 늘었습니다. Q4에서는 월 파티션이 단일 테이블보다 두 배 넘게 느렸습니다.

## 기법마다 맞는 질의가 따로 있다

**파티셔닝**은 기간 조건이 좁을 때 효과가 있었습니다. Q1은 3개 월 파티션만 읽어서 1,783ms가 290ms가 됐습니다. 반대로 Q4는 12개 파티션을 읽어야 해서 이득이 없었고 오히려 느려졌는데, 이유는 확인하지 못했습니다. 실행 계획만으로는 단정할 수 없었고, 추측으로 쓰고 싶지 않아서 저장소에도 "모른다"고 적어 두었습니다.

**인덱스**는 조건이 좁은 Q3에서 28배(1,757ms → 62ms) 빨라졌습니다. 그런데 한 달치 데이터(전체의 4% 정도)를 읽는 Q2에서는 계획기가 비트맵 인덱스 스캔을 골랐고, 순차 스캔보다 두 배 이상 느렸습니다. 이 실험에서는 읽어야 할 행이 많을 때 인덱스를 거치는 쪽이 불리했습니다.

**파티션과 인덱스를 같이 쓰면** 더 빨라질 것 같지만, Q1에서는 파티션만 쓴 쪽(290ms)이 둘 다 쓴 쪽(500ms)보다 빨랐습니다. 파티션이 이미 읽을 범위를 좁혀 놓은 뒤라 인덱스의 이득이 보이지 않았고 오히려 느려졌습니다. 이유까지는 확인하지 않았습니다.

**집계 테이블**은 압도적이었습니다. Q1, Q2, Q4가 6~12ms로 225~307배 빨라졌습니다. 대신 값을 치릅니다.

- 데이터가 늦습니다. 이 실험에서는 배치로 한 번 만들었고 실시간 갱신은 구현하지 않았습니다.
- 집계 단위(지역·일)에 없는 질문은 받을 수 없습니다. 도로 단위인 Q3은 집계 테이블로 답할 수 없습니다.
- 원본이 정정되면 집계를 다시 만들어야 합니다.

평균을 저장할 때는 평균값이 아니라 `속도 합계`와 `건수`를 저장했습니다. 하루 평균을 모아서 한 달 평균을 내는 순간 평균의 평균이 되어 값이 틀어지기 때문입니다.

```sql
CREATE TABLE daily_region_stats AS
SELECT (obs_time AT TIME ZONE 'Asia/Seoul')::date AS day,
       region_id,
       sum(volume)::bigint    AS total_volume,
       sum(speed_kmh::float8) AS sum_speed,
       count(*)::bigint       AS samples
FROM obs_plain
GROUP BY 1, 2;
-- 조회 시: sum(sum_speed) / sum(samples)
```

## 그 위에 API를 얹어 보니

통계는 결국 API로 나갑니다. Spring Boot로 같은 통계를 원본, 집계 테이블, 집계 테이블 + Redis 캐시로 조회하는 API를 만들고 부하를 줬습니다(동시 20, 300요청, 데이터 500만 건).

| 질의 | 원본 | 집계 테이블 | 집계 + 캐시 |
|---|---|---|---|
| Q1 | 105 req/s | 1,605 | 1,414 |
| Q2 | 9 | 1,075 | 1,600 |
| Q4 | 4 | 585 | 1,413 |

![API 처리량](/assets/images/02_api_처리량.png)

캐시가 항상 이득은 아니었습니다. Q4는 585에서 1,413 req/s로 늘었지만 Q1은 1,605에서 1,414로 차이가 없었습니다. 집계 테이블만으로 이미 충분히 빠른 질의에 캐시를 더하면 복잡성만 늘 수 있습니다.

원본과 집계 테이블이 같은 답을 내는지는 테스트로 묶어 두었습니다. 단위 테스트 14개와, 실제 PostgreSQL에서 두 방식의 결과를 비교하는 통합 테스트 3개를 CI에서 돌립니다.

### Redis를 끄니 요청당 1초가 걸렸다

캐시 장애를 가정해서 Redis 오류가 나면 DB로 바로 조회하도록 만들었습니다. 요청은 전부 성공했습니다. 그런데 Redis를 실제로 껐더니 p50이 11ms에서 1,018ms로 늘고 처리량이 17.9 req/s까지 떨어졌습니다. 요청마다 캐시 읽기와 쓰기 타임아웃을 연달아 기다리고 있었습니다.

오류가 나면 10초간 캐시를 건너뛰는 간단한 서킷 브레이커를 넣었습니다. 같은 상황에서 p50은 20ms, 처리량은 674 req/s가 됐고, Redis가 돌아오면 10초 안에 다시 캐시를 씁니다. 코드로는 몇십 줄이지만, 장애를 직접 만들어 보기 전에는 이 문제를 알 수 없었습니다.

| | 처리량 | p50 | 실패 |
|---|---|---|---|
| 정상 (캐시 사용) | 1,600 req/s | 11ms | 0 |
| Redis 중단, DB로 대체만 | 17.9 req/s | 1,018ms | 0 |
| Redis 중단, 서킷 브레이커 적용 후 | 674 req/s | 20ms | 0 |

Prometheus와 Grafana로 처리량, p95·p99, 커넥션 풀, 5xx, JVM 힙을 볼 수 있게 해 두었습니다. 아래는 부하를 주는 동안의 화면입니다(Docker Compose 환경, 100만 건).

## 만들다가 틀린 것들

- 파티션 경계를 세션 시간대로 만들었더니, 시간대가 UTC인 Docker에서 데이터 적재가 실패했습니다. 한국 시간 자정으로 명시해서 고쳤습니다.
- 로컬 PostgreSQL의 WAL이 7.9GB까지 커져서 디스크가 모자랐습니다. `max_wal_size`를 낮췄습니다.

## 이 실험으로 말할 수 없는 것

- 데이터가 전부 메모리에 올라가는 크기라서, 실제 대용량에서 디스크 I/O가 지배적일 때의 효과는 재현하지 못했습니다.
- 균등 분포 합성 데이터라서 실제 데이터의 쏠림(출퇴근 시간, 특정 지역)이 없습니다.
- 쓰기 성능과 동시 쓰기, 집계 테이블의 증분 갱신은 다루지 않았습니다.
- 부하 테스트는 부하 생성기와 서버가 같은 노트북에서 돌았으니 절대값보다 상대 비교로 봐야 합니다.
