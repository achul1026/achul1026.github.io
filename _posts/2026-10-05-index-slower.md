예전에 맡았던 프로젝트에서 교통 데이터 통계 화면이 수십 초씩 걸렸다. 쿼리를 고치고, 월 단위로 파티션을 나누고, 집계 테이블을 만들고, 인덱스를 다시 잡아서 10초 안쪽으로 줄였다. 그런데 이 중 무엇이 얼마나 먹혔는지는 따로 떼어서 재 본 적이 없다.

업무 데이터는 밖으로 꺼낼 수 없으니 비슷한 모양의 가짜 데이터를 만들어서 처음부터 다시 쟀다. 규모는 많이 다르다. 이쪽은 테이블 하나가 1.7GB라서, 그때의 성과와 숫자를 나란히 놓고 비교하면 안 된다. 보고 싶었던 건 기법마다 어떤 질의에서 득이고 어떤 질의에서 손해냐는 것이다. 결과부터 적으면, 집계 테이블은 압도적이었고 인덱스와 파티션은 질의에 따라 도움이 되기도 하고 발목을 잡기도 했다.

## 어떻게 쟀나

데이터는 합성 교통 관측 기록 3,000만 건이다. 지역 31개, 기간은 2023년 1월부터 2024년 12월, 값은 균등하게 뿌렸다. PostgreSQL 18.3을 노트북 한 대(i5, RAM 8GB)에서 돌렸고, 시간은 `EXPLAIN (ANALYZE)`가 알려 주는 실행 시간이다. 한 번 워밍업하고 다섯 번 재서 중앙값을 썼다.

비교한 구성은 다섯 가지다.

- A: 단일 테이블, 인덱스 없음
- B: 월 단위 파티션, 인덱스 없음
- C: 단일 테이블 + 인덱스
- D: 월 단위 파티션 + 인덱스
- E: (지역, 일) 단위 집계 테이블

질의는 통계 화면에서 흔히 나올 법한 네 가지로 잡았다. Q1은 지역 하나의 3개월 월별 통행량, Q2는 전 지역의 한 달 일별 평균 속도, Q3은 도로 하나의 1년치 시간대별 평균 속도, Q4는 지역별 연간 통행량 순위다.

빨라졌는데 답이 틀리면 소용이 없어서, 재기 전에 모든 구성이 같은 답을 내는지부터 확인했다.

## 결과

| 질의 | A 단일 | B 월 파티션 | C 단일+인덱스 | D 파티션+인덱스 | E 집계 테이블 |
|---|---|---|---|---|---|
| Q1 | 1,783ms | 290ms | 746ms | 500ms | 5.8ms |
| Q2 | 2,525ms | 2,414ms | **5,559ms** | 2,584ms | 11ms |
| Q3 | 1,757ms | 744ms | 62ms | 47ms | - |
| Q4 | 2,947ms | **6,774ms** | 4,825ms | 4,139ms | 12ms |

![질의별 조회 시간(로그 축)](/assets/images/01_db_조회시간.png)

굵게 표시한 두 칸을 보자.

Q2에 인덱스를 걸었더니 2.5초가 5.6초가 됐다. 다섯 번 모두 5.3초에서 6.6초 사이였으니 우연히 한 번 튄 값이 아니다. 실행 계획을 열어 보면 이유가 일부 보인다. 인덱스로 후보 행을 찾는 데는 0.5초 남짓밖에 안 걸렸는데, 그렇게 찾은 120만 행을 테이블에서 읽어 오는 쪽이 3초를 넘겼다. 순차 스캔은 같은 일을 2.5초에 끝냈다. 한 달치면 전체의 4% 정도인데도 이런 결과가 나왔다.

Q4에서는 월 파티션이 단일 테이블보다 두 배 넘게 느렸다. 2024년치 12개 파티션을 읽으니 전체 3,000만 건의 절반만 읽는데도 그렇다. 병렬 워커는 양쪽 다 2개씩 떴다. 다섯 번 잰 값도 최소 4.5초에서 최대 9.1초로 흔들렸다. 이유는 아직 모른다. 실행 계획을 몇 번 훑어봤지만 이거다 싶은 단서를 찾지 못했고, 모르는 걸 아는 척 쓰고 싶지 않아서 저장소에도 모른다고 적어 뒀다.

## 파티션은 범위가 좁을 때, 인덱스는 조건이 좁을 때

Q1은 3개월만 읽으니 파티션 3개만 건드린다. 인덱스 없이도 1,783ms가 290ms가 됐다. 반대로 Q3은 도로 하나를 찍는 질의라서 인덱스가 28배(1,757ms → 62ms)를 만들었다. 둘 다 "읽을 양이 확 줄어드는" 질의다.

같이 쓰면 더 빨라질 것 같지만 Q1에서는 파티션만 쓴 쪽(290ms)이 둘 다 쓴 쪽(500ms)보다 빨랐다. 파티션이 이미 범위를 좁혀 놓은 뒤라 인덱스가 보탤 게 없었던 것 같은데, 이것도 이유까지는 확인하지 않았다.

## 집계 테이블은 값을 치른다

Q1, Q2, Q4는 집계 테이블에서 6~12ms가 나왔다. 원본 대비 225배에서 307배다. 대신 얻은 만큼 내줘야 하는 게 있다.

미리 계산해 두는 방식이라 데이터가 늦다. 이 실험에서는 배치로 한 번 만들었고 실시간 갱신은 만들지 않았다. (지역, 일)이라는 단위에 없는 질문에는 답을 못 한다. 도로 단위인 Q3이 그렇다. 원본이 정정되면 집계를 다시 만들어야 한다.

평균을 저장할 때는 평균값 대신 합계와 건수를 따로 저장했다. 일별 평균을 모아서 월 평균을 내면 평균의 평균이 되어 값이 달라지기 때문이다.

```sql
CREATE TABLE daily_region_stats AS
SELECT (obs_time AT TIME ZONE 'Asia/Seoul')::date AS day,
       region_id,
       sum(volume)::bigint    AS total_volume,
       sum(speed_kmh::float8) AS sum_speed,
       count(*)::bigint       AS samples
FROM obs_plain
GROUP BY 1, 2;
-- 조회할 때: sum(sum_speed) / sum(samples)
```

## API를 얹고 Redis를 꺼 봤다

통계는 결국 API로 나간다. Spring Boot로 같은 통계를 원본, 집계 테이블, 집계 테이블에 Redis 캐시를 붙인 방식으로 조회하는 API를 만들고 부하를 줬다(동시 20, 300요청, 데이터 500만 건).

![API 처리량(로그 축)](/assets/images/02_api_처리량.png)

원본 조회는 질의에 따라 초당 4~105건이었고 집계 테이블은 585~1,605건이었다. 캐시는 Q4에서만 확실히 도움이 됐다(585 → 1,413). Q1은 1,605에서 1,414로 오히려 조금 줄었다. 집계 테이블만으로 이미 빠른 질의에는 캐시가 보탤 게 없었다.

더 건진 건 Redis를 껐을 때다. 캐시가 죽으면 DB로 바로 가도록 만들어 뒀고 요청은 전부 성공했다. 그런데 Redis를 정말로 끄고 재 보니 p50이 11ms에서 1,018ms로 늘고 초당 처리량이 17.9건까지 떨어졌다. 요청마다 캐시 읽기 타임아웃과 쓰기 타임아웃을 연달아 기다리고 있었다.

그래서 오류가 나면 10초 동안 캐시를 건너뛰는 서킷 브레이커를 넣었다. 코드는 서른 줄 남짓이다.

| | 처리량 | p50 | 실패 |
|---|---|---|---|
| 정상 (캐시 사용) | 1,600 req/s | 11ms | 0 |
| Redis 중단, DB로 대체만 | 17.9 req/s | 1,018ms | 0 |
| Redis 중단, 서킷 브레이커 적용 | 674 req/s | 20ms | 0 |

Redis를 다시 켜면 10초 안에 캐시를 다시 쓴다. 장애를 직접 만들어 보기 전에는 몰랐을 문제였다. 처리량과 지연 분포, 커넥션 풀은 Prometheus와 Grafana로 볼 수 있게 해 뒀다. 아래는 부하를 주는 동안의 화면이다(Docker Compose 환경, 100만 건).

## 만들다가 틀린 것

파티션 경계를 세션 시간대로 만들었더니, 시간대가 UTC인 Docker에서 데이터 적재가 실패했다. 한국 시간 자정으로 못 박아서 고쳤다. 로컬 PostgreSQL의 WAL이 7.9GB까지 커져서 디스크가 모자란 적도 있다. `max_wal_size`를 낮췄다.

## 이 실험이 말해 주지 못하는 것

데이터가 전부 메모리에 올라가는 크기라서, 디스크 I/O가 지배적인 진짜 대용량에서의 효과는 재현하지 못했다. 값도 균등하게 뿌렸으니 출퇴근 시간이나 특정 지역 쏠림 같은 현실의 분포는 없다. 쓰기 성능과 집계 테이블의 증분 갱신은 다루지 않았다. 부하를 주는 쪽과 받는 쪽이 같은 노트북이라 절대값보다는 구성끼리의 상대 비교로 읽어야 한다.
