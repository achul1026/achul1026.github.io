# 편집 계획 (주 1회)

## 4주 순환 (주제를 다양하게)

| 주 | 유형 | 내용 | 라벨 |
|---|---|---|---|
| 1주 | 직접 해본 것 | 직접 만들고 측정한 실험, 프로젝트 결과 | (없음) |
| 2주 | 기술 동향 정리 | 한 주제를 출처 3~5개로 정리, 비교표와 내 의견 | `[정리]` |
| 3주 | 개념 깊게 보기 | 공식 문서 기반으로 한 개념을 파고들고 간단한 실습 코드 | (없음) |
| 4주 | 회고·트러블슈팅 | 실제 겪은 문제, 협업 방식, 학습 기록 | `[회고]` |

## 주제 영역 (돌아가며 선택)
- DB·성능: 인덱스, 파티셔닝, 쿼리 계획, 커넥션 풀, 트랜잭션 격리 수준
- 인증·보안: JWT 함정, 권한 모델, OAuth, PKI·전자서명·양자내성암호 동향
- 배치·결제: 정기 결제, 멱등성, 재시도·보상 처리
- 클라우드·배포: Docker, Kubernetes, CI/CD, 모니터링
- 아키텍처·품질: 멀티모듈, 테스트 전략, 장애 대응
- 개발 도구·AI: 개발 도구와 AI 보조 도구를 쓰는 방법과 한계
- 커리어·협업: 문서화, 코드 리뷰, 일정 관리

## 지킬 규칙
1. **직접 겪지 않은 일을 1인칭 경험처럼 쓰지 않는다.** 정리 글은 `[정리]`를 제목에 붙이고 "정리한 글"임을 첫 문단에 밝힌다.
2. 모든 정리 글에 **출처 링크**를 단다. 원문 문장을 길게 옮기지 않고 자기 말로 요약한다(직접 인용은 짧게, 따옴표와 출처 함께).
3. 수치는 **직접 측정한 것만** "측정"이라고 쓴다. 다른 곳의 수치는 출처와 함께 "발표된 수치"라고 쓴다.
4. 회사명, 발주처, 프로젝트 이름, 내부 수치는 쓰지 않는다. 업무 경험은 일반화해서 쓰고 사내 규정을 먼저 확인한다.
5. 초안은 사람이 읽고 고친 뒤에만 게시한다.

## 승인과 게시 흐름
1. 초안이 **Pull Request**로 올라온다(`_posts/YYYY-MM-DD-제목.md`, 날짜는 게시 예정일).
2. 본인이 읽고 수정이 필요하면 코멘트를 남기고, 괜찮으면 **Merge**한다. Merge가 승인이다.
3. 파일의 날짜가 오면 하루 한 번 도는 빌드가 글을 게시한다. 날짜가 이미 지났으면 바로 게시된다.
4. 승인하지 않은 글은 게시되지 않는다.
